# App bundles and resource sealing

The path APIs and CLI can sign, inspect, verify and remove signatures from a
bounded `Contents`-based macOS app layout. Production uses Go filesystem and
cryptographic code on Linux, macOS and Windows. Apple tools and Clang are used
only for research and acceptance testing. This is the first bundle phase;
frameworks, nested code and full native bundle policy remain incomplete.

## Supported layout

```text
Example.app/
  Contents/
    Info.plist
    MacOS/hello
    Resources/                 # optional; plain files and directories
    PkgInfo                    # optional
    version.plist              # optional
    embedded.provisionprofile  # optional
    _CodeSignature/
      CodeResources            # generated by signing
```

`Info.plist` must be an XML dictionary containing a nonempty
`CFBundleIdentifier`, a single filename in `CFBundleExecutable`, and
`CFBundlePackageType` equal to `APPL`. The executable must use a supported Mach-O
layout. Its filename is resolved under `Contents/MacOS`. Signing defaults to the
bundle identifier; `--identifier` or `SignOptions.Identifier` can override it.
The directory suffix alone does not determine bundle recognition.

```sh
macoscodesign -s - --timestamp=none ./Example.app
macoscodesign --verify ./Example.app
macoscodesign -dvvvv ./Example.app
macoscodesign --remove-signature ./Example.app

macoscodesign -s identity.p12 --password-file password.txt --timestamp=none ./Example.app
macoscodesign --verify --trust-root code-root.pem ./Example.app
```

Existing identity, entitlement, requirement and timestamp options feed the
Mach-O signing core. The bundle acceptance matrix covers ad-hoc and public-test
RSA identities on arm64, x86_64 and universal executables. It does not prove all
combinations of these options. Certificate and TSA trust remain explicit;
see [certificates](certificates.md) and [timestamps](timestamps.md).

`Sign`, `Inspect`, `Verify` and `RemoveSignature` accept the bundle path. The
byte APIs operate on Mach-O and UDIF data. Bundle signing and verification
read their own Info.plist and resource envelope, rejecting external special-slot
overrides. `Report.Bundle` describes the main executable, Info.plist entry count,
and envelope version/rule/file counts. Inspection metadata does not establish
validity or trust.

## Sealing and verification

Signing constructs deterministic XML `CodeResources` with Apple's non-flat
version 1 and version 2 rule dictionaries. Legacy file entries use SHA-1; modern
entries use SHA-256. The main executable binds the exact Info.plist bytes and
CodeResources bytes through CodeDirectory special slots 1 and 3.

Verification checks that binding, the executable signature and applicable trust,
the supported rule dictionaries, and every modern resource hash. Added, altered
or missing required resources fail verification. Non-Base localization files
are optional: a sealed file may be removed, but modifying it or adding another
file fails. `Base.lproj` files remain required. `PkgInfo`, localization
`locversion.plist`, and `.DS_Store` follow the tested native omission rules.
The legacy dictionary still includes Resources/.DS_Store; modern verification
uses `files2`, so changing that omitted file does not invalidate the bundle.

`--force` is required to replace a signed executable. `--dryrun` constructs the
signature without creating a signature directory or writing either output.
Construction errors, including timestamp-provider failures, precede mutation.
Successful removal strips the main signature and deletes CodeResources and the
empty signature directory; it also accepts an already unsigned supported app.

## Limits

- Only the displayed layout is supported. Frameworks, plugins, XPC services,
  helpers, nested apps/code, flat/iOS/installer bundles, receipts, extra signature
  metadata and custom resource specifications return errors.
- Bundle XML is limited to 8 MiB, 32 nesting levels and 100,000 elements.
  Duplicate dictionary keys and malformed XML structures are rejected. Binary
  Info.plist input is not yet supported.
- Paths use portable ASCII names: no traversal, Windows-reserved names,
  case collisions, trailing dots/spaces or platform-specific punctuation.
  Path limits are 1,024 bytes, 255 bytes per component and 32 separators.
  There are at most 10,000 tree entries and 1 GiB of hashed resource data;
  the existing 1 GiB Mach-O bound also applies.
- Symlinks and non-regular files are rejected. Hard links within Contents to
  either file that signing writes are rejected. Filesystem operations use
  `os.Root` for path containment. Existing inodes are preserved; external hard
  links retain their usual shared-file behavior.
- Writes to the executable and envelope are not a transaction. Write, sync,
  close or truncation failures can leave partial output. Concurrent filesystem
  mutation is unsupported; sign a copy when rollback is required.
- Extended-attribute policy, native strict-validation flags, resource-rule
  overrides, nested-code requirements, notarization and full diagnostic parity
  remain open. Default Go verification checks the supported envelope; the CLI's
  native `--strict` option is not implemented by this phase.

## Evidence

`make research-bundles` runs a Go driver that extracts verbatim Apple
`defaultResourceRules`, `ResourceBuilder::hashName` and resource flags through
Clang for arm64 and x86_64. [The AST record](../spec/apple-bundles.json) pins source,
excerpt and translation-unit hashes. Type/interface shims make these excerpts
parseable; the extractor does not execute Apple's bundle services.

[Acceptance tests](../acceptance/bundle_test.go) compare every executable and
CodeResources byte for three native ad-hoc apps, all five display verbosity
levels, and eleven resource/metadata/code mutations. Six Go-signed ad-hoc/RSA
apps pass native strict verification on the development Mac. Three committed
[native fixtures](../testdata/bundles/README.md) are verified and reproduced by
the CLI on every OS. CI additionally requires native verification of six bundles
from each Linux/Windows producer. See [progress](progress.md) for commit-specific
workflow results; configured checks are not evidence that an untested commit passed.

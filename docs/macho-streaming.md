# Streaming Mach-O signing and removal

Standalone Mach-O path operations read and hash a held source, construct small
header/signature sections, and stream the result into an APFS SDK replacement.
First signing, force re-signing, dry runs and signature removal share this path
on Linux, macOS and Windows. Thin and universal binaries use the same signature
and removal policy as the byte APIs. No production operation invokes Apple tools.

## Output and ownership

An output plan describes generated bytes, borrowed source ranges and explicit
zero-filled gaps. Its checked `int64` offsets support random access without
materializing the payload. Header replacements are visible to page hashing;
the completed signature becomes another generated section. Untouched bytes,
including native-retained old signature padding, remain source-backed. Universal
assembly emits the rewritten FAT index, alignment gaps and each slice plan.

One 64 KiB transfer buffer feeds all CodeDirectory pages, including page sizes
larger than that buffer. Load commands, signatures and FAT indexes are still
materialized. `SignBytes` and `RemoveSignatureBytes` retain independent returned
buffers and the existing 1 GiB output allocation ceiling; path operations no
longer inherit that payload ceiling. These are not constant-memory operations:
signature size grows with page and special-slot counts.

The writer borrows the preflight descriptor through transfer and metadata
restoration. Released APFS v0.17.1 owns replacement allocation, ACLs, ownership,
attributes, creation times and cleanup. Its existing held-source API suffices;
there is no new filesystem implementation or dependency in codesign. Linux uses
its metadata restoration path, Darwin its clone/fallback path, and Windows its
copy/security path. The source handle closes before rename on Windows.

Source identity, size and modification time are checked before allocation and
after payload transfer. The selected directory entry is checked before commit.
These checks detect ordinary changes; they do not create a snapshot or prevent
changes after the final check. Read/write/metadata/sync/close failures and
cancellation before rename discard staging. Successful replacement detaches
the selected hard link. Dry runs allocate and clean staging without replacing
the source or restoring staged metadata. Existing operation-specific access-time
behavior and sideband preflight remain required.

## Native size boundaries

The complete pinned Apple `assure_signature_space` body is compiled against the
host SDK for arm64 and x86_64 in [the allocation AST](../spec/apple-macho-allocation.json).
Existing [writer](../spec/apple-writer.json) and [removal](../spec/apple-removal.json)
evidence includes the enclosing allocation/deallocation functions. These use
32-bit whole-file sizes and checked signature allocation arithmetic. AST shims
are declarations only; runtime behavior comes from independent native captures.

The [native corpus](../testdata/research/large-macho.json) records complete-file
SHA-256 hashes, sizes, exit codes, diagnostics, input recipes and provenance for:

- Thin arm64 inputs one byte below, at and above 1, 2 and 4 GiB.
- Universal x86_64/arm64 inputs above 1 and 2 GiB.
- A 1 GiB-plus-one input with 4 MiB-plus-37 populated bytes beginning 17 bytes
  before the 512 MiB boundary, crossing page and transport boundaries.

Native signing succeeds around 1 and 2 GiB. Signing the captured 4 GiB-minus-one,
4 GiB and 4 GiB-plus-one inputs fails with the native internal-error diagnostic.
Removal of the unsigned 4 GiB-minus-one input succeeds unchanged in bytes;
the two larger inputs fail. The portable path reproduces those outcomes rather
than treating the former 1 GiB memory ceiling as a format limit. General FAT64
range arithmetic is unit-tested independently; it does not establish native
support for whole-file mutation above the allocator's 32-bit limit.

## Reproduction and tests

```sh
go run scripts/extract-macho-allocation.go -check -out artifacts/apple-macho-allocation.json
go run scripts/probe-large-macho.go -check -out artifacts/large-macho.json
go test -count=1 -run '^TestLargeMachOMutation$' ./acceptance
```

The native CI job recaptures every case. Each OS runs the CLI against real files,
compares entire outputs through streaming hashes, and checks diagnostics and
hard-link identity after every operation. Successful results require strict
verification; macOS also runs Apple's verifier. The nine successful signed
outputs are exported as gzip streams containing every produced byte. The native
foreign-producer job reconstructs all eighteen Linux/Windows outputs, checks
their full native hashes and verifies them with Apple codesign.

Sparse input setup is explicit on Windows. Output transfer still reads and writes
every logical byte; no sparse-extent shortcut replaces hashing or comparison.
The 30-second command deadline and all prior matrix cases remain unchanged.
The populated control is not a densely populated multi-gigabyte benchmark.
Large mutable fixtures use GitHub's provisioned `RUNNER_TEMP` scratch directory
when available and the normal temporary directory for local runs. Each case logs
its location and operation timings; Windows CI also records volume capacity and
filesystem type. File IDs are captured before mutation, including Windows' lazy
`Stat` identity lookup, so post-operation checks compare the original object.

Unit coverage includes 64-bit FAT assembly, patch boundaries, preservation of
unmodified ranges, short/invalid/failing reads, cancellation, source changes,
close failures and staging cleanup. The existing full-duration inspection
fuzzer additionally compares byte and range mutation results. A virtual
1 GiB-plus-one signing control allocated 4,306,328 Go bytes locally and has a
16 MiB regression ceiling. This is an allocation measurement, not RSS or a real
file acceptance substitute; the native corpus supplies the latter separately.
